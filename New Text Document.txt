```text

      ↓

      ↓
Serverless Worker / Scheduled Job
      ↓
Managed PostgreSQL
      ↓
Backend API
      ↓
Vercel Frontend
      ↓
Price Chart
```

Do NOT require a VPS, dedicated server, or manually managed Linux server.

* Resume after failures
* Continuously index new blocks
* Store progress/checkpoints

* Run without a VPS

### Important: long-running indexer

I understand that Vercel serverless functions are not suitable for a permanently running process.

Therefore, do NOT try to keep a serverless function alive indefinitely.

Instead, design the indexer as resumable jobs:

```text
Scheduled Job
      ↓
Read last indexed block from PostgreSQL
      ↓
Process a limited block range
      ↓
Store events
      ↓
Update checkpoint
      ↓
Exit
```

Then the next scheduled execution continues from the checkpoint.

For example:

```text
Run 1 → blocks A-B
Run 2 → blocks B-C
Run 3 → blocks C-D
...
```

After the historical backfill reaches the chain head, the same system should periodically process new blocks.

If a better managed/serverless architecture exists, use it, but it must not require a VPS.

### PostgreSQL

Use a managed PostgreSQL service.

Design the schema for:

* markets
* market price history
* liquidity events
* indexed blocks/checkpoints
* block timestamps

Use proper indexes and unique constraints.

The indexer must be idempotent, so running the same job twice must not create duplicate events.

### Backfill

The historical range is approximately:

```text
55,632,013 → 57,300,000+
```

Do NOT scan this entire range in one RPC request.

Automatically determine a safe chunk size based on Arc RPC limitations.

Handle:

* HTTP 429
* RPC errors
* temporary failures
* range-limit errors
* retries with exponential backoff
* adaptive chunk sizing if necessary

The backfill must be resumable.

If the job stops at block X, the next execution must continue from X rather than starting over.

### Continuous indexing

After backfill:

```text
Scheduler
   ↓
Read latest indexed block
   ↓
Read new blockchain events
   ↓
Insert into PostgreSQL
   ↓
Update checkpoint
```

The system should continuously stay close to the Arc chain head.

Do not make the frontend responsible for indexing.

### Block timestamps

Do not make the browser call getBlock for every event.

The indexer should obtain block timestamps server-side and cache them in PostgreSQL.

If multiple events belong to the same block, fetch the block timestamp only once.

The current flow is:

```text
Frontend → RPC → scan ~1.7M blocks → chart
```


The frontend should require little or no RPC access for historical chart data.
